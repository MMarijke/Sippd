# Sippd Data Safety Mapping

Reference table of every category of user data collected or transmitted by Sippd, for filling out the **Google Play Data Safety form** and the **Apple App Privacy questionnaire** (if iOS is added later). Compiled directly from the current codebase, not from the general product description — see the source noted for each row if you need to re-verify.

| Data type | What it is | Why it's collected | Linked to identity | Shared with third parties | Required or optional |
|---|---|---|---|---|---|
| **Email address** | Your login email, collected via Supabase Auth at signup. | Core functionality — account creation and authentication. | Yes | Supabase (as the auth/database processor only — not sold, not shared for advertising). Also sent to Paddle if you subscribe to Sippd Pro, so your subscription can be linked to your account. | Required — you must have an account to use the App. |
| **Display name** | The name shown on your profile, leaderboards, and the activity feed. | Core functionality / personalization — identifies you to other users. | Yes | Stored via Supabase; visible to other Sippd users as part of the App's own social features (not shared with an external third party). | Optional — starts blank at signup (`full_name: ''`); the UI falls back to a generic label ("Collector") until you set one. |
| **Can photos** | Photos of energy drink cans you add to your collection, uploaded to Supabase Storage (or a URL you supply). | Core functionality — collection cataloging and showcase. | Yes — tied to your collection, and visible to others if your profile is public. | Supabase (storage). Not shared with any other third party. | Optional — a can can be logged without a photo. |
| **Barcode data** | The barcode number scanned when you log a can. | Core functionality — product lookup during scan-to-log. | No — only the bare barcode number is sent, with no user identifier attached. | Open Food Facts (lookup only; not stored by Sippd beyond the resulting can record you choose to save). | Optional — only sent if you use barcode lookup; manual entry is also available. |
| **Rarity votes** | Which rarity tier you voted a given can as. | Core functionality — feeds the community rarity consensus. | Yes — one vote per user per can, enforced server-side. | Supabase. Your individual vote isn't shown to other users; only the aggregated consensus is. | Optional. |
| **Reactions** | Emoji reactions (fire / star / wow) you leave on activity feed posts. | Core functionality — social engagement. | Yes — one reaction per user per post. | Supabase; visible to other users viewing the feed. | Optional. |
| **Follows** | Which other users you follow — your social graph on Sippd. | Core functionality — social/competitive features. | Yes | Supabase; follow relationships are visible within the App's social features. | Optional. |
| **Streak / last-active data** | Your current login streak and last-active date. | Core functionality / gamification. | Yes | Supabase; may be visible to other users (for example, on a shared collection card). | Not user-provided — derived automatically from app usage; no opt-out while using the App. |
| **Region** | An optional region you can set on your profile. | Personalization — powers the regional leaderboard. | Yes | Supabase; visible to other users if set. | Optional. |
| **Subscription/billing data** | Your Paddle subscription ID, Paddle customer ID, and subscription status (free/pro/cancelled), stored on your profile once you subscribe to Sippd Pro. | Core functionality — required to grant and manage paid-tier (Sippd Pro) access. | Yes | Paddle, acting as Merchant of Record for the transaction — your payment method and card details are handled entirely by Paddle and never reach Sippd's own servers. Supabase stores the IDs/status Paddle reports back. | Optional — only collected if you subscribe to Sippd Pro. |
| **Crash/error data** | Diagnostic data captured when the App errors. | Analytics — stability and bug-fixing, not advertising or personalization. | Split by surface. Backend (edge functions, `supabase/functions/_shared/sentry.ts`): No — `event.user` is deleted outright, `dataCollection: { userInfo: false }` is set, and the `DenoServe`/`RequestData` integrations (which would otherwise auto-capture request/IP data) are removed entirely. Frontend (browser, `src/main.jsx`): Possibly — `beforeSend` only strips `user.email`/`username`/`ip_address`, fields that are rarely populated in the first place since `Sentry.setUser()` is never called anywhere in the codebase; it does not scrub breadcrumbs or the request URL, and Supabase's REST client embeds the calling user's own account UUID directly in the query string for most owner-scoped reads (e.g. `?owner_id=eq.<uuid>`), so a browser error's breadcrumb trail can carry that UUID even with no name/email attached. | Sentry, with PII stripped before sending (see previous column for what "stripped" actually covers on each surface). | Not user-provided — collected automatically when errors occur; no separate opt-in/out currently implemented. |
| **IP address / device info** | Standard web request logs (IP address, browser/device details, timestamps). | Primarily standard infrastructure-level request logging performed by Vercel (hosting) and Supabase (backend) as part of their own platform operation, for security/operational purposes (abuse prevention, debugging, rate limiting) — not something most of Sippd's own application code reads or acts on. One exception: the `image-proxy` edge function (`supabase/functions/image-proxy/index.ts`) deliberately reads the caller's IP (`x-forwarded-for`, falling back to `x-real-ip`) to enforce a per-IP rate limit (60 requests/hour, via Upstash Redis) — its primary abuse control, since the function is anonymous by design (`verify_jwt` off, called from a plain `<img src>` tag with no Authorization header) and has no other identifier available to rate-limit by. That IP is used only as a transient Redis rate-limit key and is never written to Sippd's own database or logged. | Not linked to a Sippd account by the app's own code — `image-proxy`'s rate limiting is intentionally anonymous (no JWT or user id anywhere in that request path), and nothing in this codebase cross-references Vercel/Supabase's own infrastructure logs against Sippd's user table. IP addresses are still commonly treated as personal data in their own right under POPIA/GDPR-style frameworks regardless of this — see the note below. | Vercel (hosting) and Supabase (backend), as part of their own standard infrastructure-level logging, plus Upstash (via `image-proxy`'s rate limiter, IP only, not persisted). | Not user-provided — inherent to any web/app request; not something a user can opt out of while using the App. |

## How the two previously-outstanding flags were resolved

Both were verified directly against this codebase's actual configuration (2026-09-17), not inferred from general Sentry/Vercel behavior. Re-check these same files if either integration changes:

**Crash/error data — "linked to identity":** Read `src/main.jsx` (frontend Sentry init) and `supabase/functions/_shared/sentry.ts` (backend edge-function Sentry init) directly. The backend is thoroughly scrubbed (`event.user` deleted, IP-capturing integrations removed, headers/messages scrubbed). The frontend is not fully scrubbed: its `beforeSend` only strips fields off `event.user` that are essentially never populated (no `Sentry.setUser()` call exists anywhere in the codebase), and doesn't touch breadcrumbs — which, because Supabase's REST client puts filter values straight into the request URL, can carry the current user's own account UUID for most owner-scoped reads. This is a real, currently-unaddressed gap if a firm "No" is wanted here — closing it would mean adding a breadcrumb/URL-scrubbing step to `src/main.jsx`'s `beforeSend` (e.g. stripping query strings from breadcrumb `data.url`), which hasn't been done as of this note.

**IP address / device info — "why it's collected" and "linked to identity":** Grepped the codebase for IP-header reads (`x-forwarded-for`, `x-real-ip`) across `src/` and `supabase/functions/`. Found three call sites: `supabase/functions/paddle-webhook/index.ts` reads IP to verify a webhook request genuinely came from Paddle's own infrastructure (an allowlist check on the *caller*, not user data, and not relevant to this row); `supabase/functions/delete-account/index.ts` and `get-subscription-status/index.ts` rate-limit by `user.id`, not IP. Only `supabase/functions/image-proxy/index.ts` reads a real Sippd user's IP, specifically as an Upstash rate-limit key for its intentionally anonymous, unauthenticated proxy endpoint — confirmed via its own file-header comment ("Anonymous by design... verify_jwt is off for this function") and the `Ratelimit.slidingWindow(60, '1 h')` config next to it.


## Notes

- This table reflects **what the codebase actually does** as of this session, not aspirational or planned behavior. Paddle billing has been live since 2026-09-01 (see the **Subscription/billing data** row above) — this table previously and incorrectly claimed monetization wasn't live yet; that claim is now corrected. (/impeccable critique)
- The **IP address / device info** row previously claimed IP data was "not something Sippd's application code explicitly captures or exposes itself" — that was inaccurate. `image-proxy`'s rate limiter does deliberately read a caller's IP; corrected 2026-09-17 (see "How the two previously-outstanding flags were resolved" above).
- "Shared with third parties" above distinguishes between (a) a data processor operating the App's own infrastructure (Supabase, Vercel, Sentry, Open Food Facts) and (b) data made visible to *other Sippd users* through the App's own social/competitive features. Google's and Apple's forms generally only ask about (a); don't conflate the two when filling them out.
